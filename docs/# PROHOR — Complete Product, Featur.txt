# **PROHOR — Complete Product, Features, AI & UI/UX Master Blueprint**

Product Specification v1.0 | 14 November 2026 | Five-member hackathon team

This is the consolidated blueprint for **PROHOR | প্রহর**, bringing together our decisions about the eight modules, 24 long-term capabilities, pregnancy-related conditions, mother-and-baby health, accessibility, AI, wellness, UI/UX, and development strategy.

I am also resolving one important inconsistency in our earlier discussions: **we no longer need two public sections called "Standard Care" and "Personalized Care."** The final design will have one shared healthcare experience with optional accessibility customization for everyone.

### **What PROHOR actually is**

PROHOR is not merely:

- A pregnancy tracker.
- A medical chatbot.
- A disability-specific application.
- A fitness or mental-health tracker.
- A hospital booking website.

**It is one connected maternal-care ecosystem incorporating all of these functions where appropriate.**

A mother can record her health information, understand medical reports, manage pregnancy-related conditions, track physical and emotional well-being, ask educational questions, and connect with human support.

An accessibility layer ensures those services can be used through different interaction methods.

### **What happens for mothers with disabilities?**

A mother who needs screen-reader or keyboard access can already operate the welcome page. These are **baseline requirements, not optional modes**.

A mother who wants AAC, reduced motion, larger controls, simplified wording or an alternative layout can configure those features before proceeding or while completing a task.

A mother without disabilities can select exactly the same preferences.

W3C recommends familiar patterns, predictable controls, short routes to important tasks and personalization without unnecessary cognitive effort.&#x20;

## **Module 01 — PROHOR Adapt**

## **Universal Access & Interaction Engine**

The foundation of every other module

**Meaning:** Adapt is the system that lets mothers choose how they read, navigate, communicate and interact with PROHOR.

It is not a disability-detection system.

### **Feature specification**

| Feature                          | What it does                                                                       | Priority |
| -------------------------------- | ---------------------------------------------------------------------------------- | -------- |
| Universal accessibility baseline | Semantic pages, keyboard operation, screen-reader compatibility, meaningful labels | P0       |
| Language preferences             | Bangla and English interface support                                               | P0       |
| Text preferences                 | Adjustable text size and readable content spacing                                  | P0       |
| Layout preferences               | Compact and spacious presentation options                                          | P0       |
| Contrast controls                | Offers accessible visual contrast options                                          | P0       |
| Reduced motion                   | Respects user and system animation preferences                                     | P0       |
| Interaction preferences          | Remembers selected reading and communication methods                               | P0       |
| Simple-Bangla content            | Displays reviewed, easier-to-read instructions                                     | P1       |
| AAC communication                | Picture-and-text message composition                                               | P1       |
| Read-aloud                       | Optional text-to-speech for supported content                                      | P1       |
| Guided task mode                 | Breaks complicated tasks into manageable steps                                     | P1       |
| Advanced assistive input         | Additional switch, speech and external AAC compatibility testing                   | P2       |

### **How this serves different users**

A blind mother can operate the website using a compatible screen reader without enabling a special mode.

A deaf mother can access all essential information in text.

A non-speaking mother can compose questions using a keyboard or supported AAC interface.

A mother with limited dexterity can use keyboard navigation and larger controls.

A mother who prefers simpler instructions can enable guided steps.

A mother with several access needs can combine preferences.

**AI requirement:** Low. The core accessibility engine must work without an AI model. AI may assist with rewriting noncritical educational content, but essential medical wording must be verified.

**Originality:** Accessibility preferences persist across all modules, rather than existing only as an isolated settings page.

## **Module 02 — PROHOR Barta**

## **Evidence-Grounded Bangla AI Companion**

Barta / বার্তা — communication and information

**Meaning:** Barta is an educational AI assistant that helps mothers understand pregnancy, medical terminology, and available care information.

### **Feature specification**

| Feature                                 | What it does                                                        | Priority |
| --------------------------------------- | ------------------------------------------------------------------- | -------- |
| Bangla text assistant                   | Answers supported maternal-health educational questions             | P0       |
| Curated knowledge retrieval             | Finds relevant information from a reviewed knowledge collection     | P0       |
| Visible references                      | Links answers to the source material used                           | P0       |
| Insufficient-evidence handling          | Says when approved information cannot answer a question             | P0       |
| Accessibility-aware responses           | Presents answers in supported formats and reading styles            | P0       |
| Consultation question preparation       | Helps mothers prepare questions for their clinicians                | P1       |
| AAC-to-question input                   | Converts a user-approved symbol selection into a text question      | P1       |
| Bangla voice input                      | Optional speech-to-text interaction                                 | P1       |
| Read-aloud responses                    | Optional audio for supported languages                              | P1       |
| Privacy-controlled conversation history | Saves previous educational conversations with the user's permission | P1       |
| Expanded postpartum knowledge           | Adds clinically reviewed content for the period after childbirth    | P2       |

### **Why AI belongs here**

A fixed FAQ cannot easily handle the variety of everyday Bangla questions, vocabulary, incomplete phrases, and communication methods that mothers may use.

A language model paired with **Retrieval-Augmented Generation (RAG)** can help produce relevant, understandable explanations grounded in reviewed documents.

### **AI workflow**

**Mother's question**

Text, supported voice or AAC

**Search approved knowledge**

**Generate a grounded explanation**

**Answer + source + accessible presentation**

**Important:** Barta must not diagnose pregnancy complications, prescribe medication, or reassure someone that they are medically safe.

WHO's guidance on healthcare AI emphasizes defined tasks, reliability, human oversight, privacy and protection against inappropriate reliance on automated outputs.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://www.who.int\&sz=32)

who.int+1



**Originality:** Barta understands the user's chosen communication method while keeping evidence requirements the same for everyone.

## **Module 03 — PROHOR Shonket**

## **Maternal Safety & Human Assistance**

Shonket / সংকেত — signals and communication of concerns

**Meaning:** Shonket helps mothers access reviewed safety information, express health concerns, and request appropriate human assistance.

| Feature                            | What it does                                                             | Priority |
| ---------------------------------- | ------------------------------------------------------------------------ | -------- |
| Maternal warning-sign information  | Displays clinician-reviewed safety guidance                              | P0       |
| Accessible help entry              | Makes help information accessible without requiring speech               | P0       |
| Concern reporting                  | Allows a mother to describe a concern through text or structured choices | P0       |
| Human-support requests             | Sends authorized requests to a provider workflow                         | P0       |
| Request status                     | Distinguishes submitted, delivered, acknowledged and responded states    | P0       |
| Communication preferences          | Tells providers how the mother prefers to be contacted                   | P0       |
| Care history                       | Shows previous support requests                                          | P1       |
| AI-assisted message drafting       | Produces a reviewable summary of a mother's own words                    | P1       |
| Advanced clinical decision support | Requires separate clinical validation and governance                     | P2       |

### **Safety interaction**

Suppose a mother is worried about a new symptom.

She should not be forced to describe it to an AI before accessing urgent-care information.

Shonket should provide a clearly marked path to reviewed urgent-care instructions, along with the ability to communicate with human support where an actual service is available.

CDC guidance recommends immediate medical care for urgent maternal warning signs during pregnancy and up to one year after delivery.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://www.cdc.gov\&sz=32)

CDC+1



**AI requirement:** Not essential for safety decisions. Use reviewed content and validated workflows; AI may help draft non-diagnostic communication summaries.

**Originality:** Human assistance is available through alternative communication methods, while delivery status remains explicit.

## **Module 04 — PROHOR Jibonrekha**

## **Connected Mother & Baby Health Records**

Jibonrekha / জীবনরেখা — continuity through the care journey

**Meaning:** Jibonrekha is the central health-record system, connecting pregnancy history, maternal conditions, fetal assessments and later newborn health information.

This is where your additional ideas about **diseases and medical conditions affecting both mother and baby** belong.

### **Maternal health features**

| Feature                     | Description                                                                     | Priority |
| --------------------------- | ------------------------------------------------------------------------------- | -------- |
| Pregnancy timeline          | Gestational week and pregnancy-stage information                                | P0       |
| Health measurements         | Records selected measurements with dates and units                              | P0       |
| Maternal conditions         | Stores clinician-confirmed diagnoses and related records                        | P0       |
| Symptoms and notes          | Records information the mother wants to discuss with a clinician                | P0       |
| Medical appointments        | Stores upcoming and completed care visits                                       | P0       |
| Health history              | Shows chronological measurements and records                                    | P0       |
| Report-linked history       | Connects verified document information to the timeline                          | P1       |
| Medication record           | Records clinician-provided prescriptions and instructions without changing them | P1       |
| Postpartum recovery records | Extends maternal records beyond delivery                                        | P2       |

### **Baby health features**

| Feature                              | Description                                             | Priority |
| ------------------------------------ | ------------------------------------------------------- | -------- |
| Baby record                          | Creates a separate but linked fetal/newborn record      | P0       |
| Clinician-recorded fetal assessments | Stores documented ultrasound findings and related notes | P1       |
| Baby-movement observations           | Lets the mother record changes or observations          | P1       |
| Documented fetal concerns            | Stores findings entered or confirmed by clinicians      | P1       |
| Newborn health record                | Continues the baby's record after birth                 | P2       |
| Growth and visit history             | Records newborn measurements and appointments           | P2       |
| Immunization history                 | Tracks documented vaccinations and schedules            | P2       |

### **Condition tracking**

Potential maternal condition categories include:

- Gestational diabetes.
- Pregnancy-related hypertension.
- Anemia.
- Other clinician-confirmed pregnancy-related conditions.
- Existing medical conditions relevant to prenatal care.

For the baby, PROHOR should store clinician-documented fetal concerns and assessments—not attempt to diagnose fetal disease from maternal activity, a photograph, or unvalidated algorithms.

### **Mother and baby: One connected timeline, separate clinical facts**

**Mother's Health**

Conditions, symptoms, measurements, medical visits, reports

**Baby's Health**

Clinician-recorded fetal assessments and later newborn records

**AI requirement:** Optional. Accurate record storage does not need AI. Later, AI can prepare factual summaries from verified records.

**Originality:** A connected, accessible mother-and-baby timeline that remains consistent across pregnancy, delivery and early motherhood.

WHO's antenatal Digital Adaptation Kit provides a useful framework for data elements, workflows, user scenarios and functional requirements, although implementation must be adapted to local clinical practice.&#x20;

## **Module 05 — PROHOR Bujhi**

## **Accessible Medical Report Understanding**

Bujhi / বুঝি — helping mothers understand information

| Feature                         | Description                                                     | Priority |
| ------------------------------- | --------------------------------------------------------------- | -------- |
| Report upload                   | Accepts supported report images or PDFs                         | P1       |
| OCR and structured extraction   | Extracts selected text, fields, numbers and units               | P1       |
| Extraction verification         | Allows the mother or authorized reviewer to correct values      | P1       |
| Medical terminology explanation | Explains supported report terms using approved references       | P1       |
| Accessible report view          | Presents structured text compatible with assistive technologies | P1       |
| Mother/baby record association  | Saves verified information into the appropriate record          | P1       |
| Report history                  | Stores approved medical documents with proper permissions       | P1       |
| Broader report-format support   | Expands extraction after testing additional formats             | P2       |

### **Full interaction**

**Upload → Extract → Review → Explain → Save to the correct record.**

A user must be able to correct a misread number before the information becomes part of the health timeline.

**AI requirement:** High for flexible document extraction and language explanation.

**Originality:** The report reader is not standalone. It converts verified medical information into accessible explanations and connects it to the longitudinal mother/baby record.

For the first MVP, support only a limited number of synthetic report formats and explicitly disclose that limitation.

Shusthota / সুস্থতা — accessible well-being

This module combines the previous emotional companion, diary, daily activity, and your expanded pregnancy fitness ideas.

### **Feature specification**

| Feature                            | Description                                                               | Priority |
| ---------------------------------- | ------------------------------------------------------------------------- | -------- |
| Daily mood check-in                | Optional private mood recording                                           | P0       |
| Energy and fatigue log             | Records self-reported energy levels                                       | P0       |

| Rest and sleep journal             | Records self-reported rest patterns                                       | P0       |
| Personal diary                     | Stores optional notes and reflections                                     | P0       |

| Ability-aware activity preferences | Lets mothers select activities relevant to their routines and limitations | P1       |
| Wellness history                   | Shows previous entries without judgmental scoring                         | P1       |
| Reviewed relaxation resources      | Provides appropriate educational content                                  | P1       |
| Optional provider sharing          | Shares selected entries only with authorization                           | P1       |
| AI-generated wellness summaries    | Summarizes recorded patterns without diagnosing a condition               | P2       |
| Clinician-approved activity plans  | Integrates professionally reviewed plans for individual circumstances     | P2       |

### **How fitness works for different mothers**

| Mother's preference or situation    | PROHOR response                                                    |
| ----------------------------------- | ------------------------------------------------------------------ |
| Walks regularly                     | Can record walking                                                 |
| Uses a wheelchair                   | Can record other meaningful activities                             |
| Needs assistance with movement      | Can record assisted activity                                       |
| Has clinician-directed restrictions | Can record rest and follow the clinician's documented instructions |
| Experiences fatigue                 | Can pause or skip a check-in                                       |
| Does not want activity tracking     | Can disable it                                                     |

**No compulsory step target. No disability-based ranking. No guilt-inducing streaks.**

Physical activity guidance during pregnancy must consider individual medical circumstances. PROHOR should not generate unreviewed exercise prescriptions.

### **Mental well-being**

The emotional support interface should allow mothers to communicate feelings privately without assuming that a mood entry establishes a diagnosis.

An important privacy decision: **private emotional diaries are not automatically shared with caregivers, family members or providers.**

**AI requirement:** Optional. Well-being logging and trend visualization work well without AI.

**Originality:** Ability-aware physical and emotional wellness, rather than a one-size-fits-all fitness score.

### **Example permission control**

A mother may allow a supporter to:

- See appointment details.
- Help request a visit.
- Receive a specific notification.

She may decide **not** to share her private diary, full medical documents, or AI conversation history.

The application must not automatically treat disability as permission for another person to control her healthcare information.

**AI requirement:** Useful for preparing verified summaries, but not required for access control or request delivery.

**Originality:** User-controlled care coordination designed around direct accessible communication.

# **6. Complete AI strategy**

AI should support clearly defined tasks. It must not become the foundation of every feature simply to increase the AI count.

| Module     | AI role                             | Necessity | MVP strategy                                    |
| ---------- | ----------------------------------- | --------- | ----------------------------------------------- |
| Adapt      | Optional explanation simplification | Low       | Build accessibility with normal software        |
| Barta      | Retrieval-based educational answers | **High**  | Implement a working, restricted RAG assistant   |
| Shonket    | Draft communication summaries       | Low       | Use reviewed safety guidance and human requests |
| Jibonrekha | Record summaries                    | Medium    | Build database and records first                |
| Bujhi      | OCR and report explanation          | **High**  | Support a limited synthetic document format     |
| Shusthota  | Non-diagnostic trend summaries      | Low       | Build ordinary tracking first                   |
| Poth       | Optional natural-language search    | Low       | Build reliable directory and filters            |
| Bondhon    | Care handoff summaries              | Medium    | Implement provider workflow before AI summaries |

## **One shared AI architecture**

**PROHOR application**

Text • Voice where supported • AAC • Documents

**Authentication, consent and request validation**

**Knowledge retrieval**

Curated sources and indexed passages

**Approved record access**

Only necessary, authorized fields

**Task-specific AI processing**

Explanation • Extraction • Summary

**Evidence checks, human review and accessible output**

### **Rules for every AI result**

AI answers must distinguish educational information from individual medical advice.

Extracted report data must remain unverified until reviewed.

AI summaries must preserve dates, measurements, record sources and consent boundaries.

Answers without adequate evidence must be allowed to abstain.

AI must not infer a mother's competence, disability, clinical condition or decision-making rights from her communication method.

| Card design        | Simple surfaces, restrained borders, subtle shadows             |
| Main buttons       | Clear verb labels and comfortably large targets                 |
| Accessibility      | WCAG 2.2 AA as the target                                       |
| Body-text contrast | At least 4.5:1 for ordinary text                                |

# **10. How different mothers complete the same workflow**

We will not maintain separate business logic for disabled and non-disabled mothers.

Instead, we test the same journeys using different interaction preferences.

| Scenario                             | Interaction requirements                                                                   |
| ------------------------------------ | ------------------------------------------------------------------------------------------ |
| A mother using conventional controls | Standard visual interface, text entry, direct navigation                                   |
| Blind mother                         | Screen reader, accessible headings, labeled forms, structured health data                  |
| Low-vision mother                    | Zoom, reflow, contrast, flexible text size                                                 |
| Deaf mother                          | Text-based AI and support, captions and visual notifications                               |
| Deafblind mother                     | Structured text compatible with assistive technologies, including supported braille access |
| Non-speaking mother                  | Text and AAC composition without voice requirements                                        |
| Mother with reduced dexterity        | Keyboard/switch-compatible interaction and forgiving targets                               |
| Mother with tremors                  | Separated controls, review and Undo                                                        |
| Mother who prefers cognitive support | Guided steps, simple explanations and predictable layouts                                  |
| Mother with sensory sensitivities    | Reduced motion and controlled interruptions                                                |
| Mother with memory difficulties      | Clear progress, summaries and Save for later                                               |
| Mother with fatigue                  | Short tasks, no unnecessary time pressure                                                  |
| Mother with multiple access needs    | Independent, combinable settings                                                           |

A disability category never automatically determines a user's language complexity, medical consent or decision-making ability.

## **Example complete care journey**

1. **Enter PROHOR**

   The mother opens the same accessible website as everyone else.
2. **Choose a task**

   She chooses to manage a health condition.
3. **Apply optional access preferences**

   She enables any communication or presentation tools she wants.
4. **Open her health record**

   She selects a clinician-confirmed maternal condition.
5. **Add information**

   She enters or reviews a health observation.
6. **Understand medical terminology**

   She asks Barta for an evidence-grounded educational explanation.
7. **Prepare a care request**

   She selects what information may be shared.
8. **Contact human support**

   Bondhon sends the authorized request through an implemented channel.
9. **Follow the request**

   She sees whether it has been delivered, acknowledged or answered.

The mother can change communication preferences at any point without starting again.

| Data entity           | What it stores                                                            |
| --------------------- | ------------------------------------------------------------------------- |
| `user_profiles`       | Account and basic profile                                                 |
| `access_preferences`  | Reading, navigation, language, communication and presentation preferences |
| `pregnancy_records`   | Pregnancy-stage and appointment-related information                       |
| `maternal_conditions` | Clinician-confirmed diagnoses and source details                          |
| `health_observations` | Measurements and symptoms with time and source                            |
| `baby_records`        | Fetal/newborn information associated with the mother                      |

| `wellness_entries`    | Optional mood, fatigue, rest and activity records                         |

The system needs a record-source field distinguishing **self-reported**, **document-extracted**, **clinician-entered**, and **clinician-confirmed** information.

Do not silently convert a mother's notes or AI-generated explanations into confirmed clinical diagnoses.

## **Permission model**

**Mother**

Controls her own information and permissions

**Chosen supporter**

Only explicitly permitted actions or records

**Authorized provider**

Only records needed and authorized for the care workflow

The server—not the visible interface—must enforce these permissions.

For the hackathon, use synthetic patient records and simulated provider accounts.

### **Error and recovery requirements**

For every workflow, we must also design what happens when:

- The connection fails.
- A user makes a data-entry error.
- AI cannot verify an answer.
- Report extraction is incorrect.
- A health entry is partially completed.
- The mother changes accessibility preferences.
- A provider cannot be reached.
- A consent request is denied or revoked.

Offline-saved information must be visibly distinguished from information successfully synchronized. An unsent help request must never be displayed as delivered.

W3C's form guidance recommends clear labels, validation, correction and confirmation for important user actions.&#x20;

# **15. What genuinely makes PROHOR unique?**

We should not claim that pregnancy tracking, health education, medical report reading, AAC, or wellness tracking are individually unprecedented.

The proposed differentiation is their **connected implementation**.

**Universal access embedded throughout healthcare**

Instead of creating disability-specific healthcare pages, PROHOR allows mothers to use the same tasks with different communication and interaction methods.

**Connected maternal and baby condition histories**

Mother and baby records remain clinically distinct while forming one continuous care journey.

**Ability-aware physical and emotional wellness**

Mothers can track meaningful routines without being ranked against universal movement or fitness targets.

**Evidence-grounded, accessible AI**

Medical information is retrieved from approved references and communicated in a format suitable for the user's preferences.

**Mother-controlled human care coordination**

The mother can choose how to communicate and which information to share with authorized support people.

To make these genuine differentiators rather than marketing claims, we need working demonstrations and accessibility testing.

# **16. The final demonstration scenario**

The best proof of PROHOR is not showing all 24 capabilities one by one.

It is showing two mothers completing the same healthcare task through their preferred interaction methods.

### **Fictional demonstration**

**Ayesha** prefers a conventional dashboard and typed communication.

**Nusrat** uses a wheelchair and prefers keyboard controls with optional AAC communication.

Both open the same PROHOR website.

Ayesha goes directly to My Health.

Nusrat opens her optional interaction preferences and enables AAC.

Both access pregnancy records, medical education and wellness tools.

Nusrat uses a picture-and-text communication workflow to ask a question. Barta returns a source-grounded written explanation.

She then chooses to share selected information with a simulated healthcare worker.

The care request appears in the provider portal, where it can be acknowledged.

**What judges should understand:** These are not separate applications, different levels of healthcare, or AI-generated disability classifications. They are two interactions with the same accessible system.

# **17. Final project blueprint summary**

# **PROHOR**

Universal Adaptive AI Maternal & Child Care Ecosystem

### **Product structure**

One inclusive application, eight integrated modules, and 24 long-term capabilities.

### **Interaction structure**

Task-first navigation, accessible by default, with optional combinable preferences available everywhere.

### **Healthcare structure**

Connected maternal and baby records, condition tracking, daily wellness, medical information and professional-care coordination.

Source-grounded maternal education and restricted report interpretation, with optional verified summaries—not autonomous clinical decision-making.

Premium desktop-first presentation that remains responsive, minimalist, Bangla-friendly, calm and accessible.

Seven-day five-member MVP sprint, continuous integration, accessibility and safety testing, followed by progressive expansion.

## **What the development team should use this blueprint for**

This document defines the **product scope, feature ownership, interface structure, AI boundaries, data relationships, accessibility behavior, and initial delivery priorities**.

The next concrete design deliverable should be a complete Figma specification covering the **welcome page, access-preference panel, care dashboard, Barta conversation, mother-and-baby health timeline, and Bondhon assistance request**.
